When running the `haml` test suite on TruffleRuby, nearly half the tests failed on CI - 162 out of 370 tests - all crashing with the exact same error: `Haml::SyntaxError: Unbalanced brackets`. What initially looked like a straightforward bug turned into a deep dive across three codebases - uncovering a 15-year-old CRuby parser quirk, an intentional design divergence in the new Prism parser, and a clever trick Haml uses to parse syntactically invalid Ruby code. Here is the story of how we tracked it down and fixed it across the ecosystem.

Every single failure produced the exact same error:

```text

Haml::Engine::old attributes::html escape#test_0001_escapes attribute values on static attributes:
Haml::SyntaxError: Unbalanced brackets.
```

## The Misleading Backtrace

A quick search across the codebase pointed to `Haml::Parser#balance_tokens` - the only place where `Haml::SyntaxError` with the message `"Unbalanced brackets"` was raised.

Curiously, the backtrace didn't mention `Haml::Parser` at all. The error seemed to originate directly inside a dynamic method generated by Tilt (`Tilt::CompiledTemplates#__tilt_46344`). This happens because Haml catches template parsing errors during compilation and turns them into embedded Ruby `raise` statements within the compiled template code. That way, syntax errors are deferred and raised when the template is evaluated at runtime.

To understand why this broke on TruffleRuby, we need to look at how Haml parses HTML tag attributes and a clever parsing trick it relies on.


## The Mystery of Haml's `a(` Trick

To understand the bug, we first have to look at how Haml parses HTML tag attributes. In Haml, attributes are written in a Hash-like syntax:

```haml
%input{:selected => true}
```

Which compiles to HTML:

```html
<input selected='selected'>
```

In general, tag attributes can be followed by static text that needs to be stripped away:

```haml
%a{:title => @title, :href => href} Profile
```

Here, the parser needs to extract `{:title => @title, :href => href}` while discarding the tag name `%a` and the suffix `" Profile"`.

At first glance, you might think Haml could simply parse the attributes as a standard Ruby `Hash` literal. But Haml syntax supports a special feature: embedding variable hashes directly into the attribute list and merging them with explicit key-value pairs:

```haml
%a{ user_attributes, :title => @title, :href => href } Profile
```

Here is the catch: `{ user_attributes, :title => @title }` is invalid Ruby syntax. In Ruby, you cannot start a hash literal with a bare variable without a key or double splat (`**`).

However, if you write it as a method call - `a( user_attributes, :title => @title )` - it becomes valid Ruby syntax, where `user_attributes` is a positional argument and `:title => @title` is parsed as trailing hash / keyword arguments.

To avoid writing a complex custom parser, Haml's authors came up with a clever shortcut: replace the opening `{` with `a(`, transforming the attribute string into an unclosed method invocation like `a( user_attributes, :title => @title }`, and pass it to Ruby's standard lexer to find where the attributes end.


## How Haml Balances Tokens

With the `a(` prefix in place, Haml delegates token scanning to `#balance_tokens`:

```ruby
def parse_old_attributes(text)
  # ...
  balanced, rest = balance_tokens(
    text.sub(?{, METHOD_CALL_PREFIX),
    :on_embexpr_beg,
    :on_embexpr_end,
    count: 1
  )
  attributes_hash = balanced.sub(METHOD_CALL_PREFIX, ?{)
  # ...
  return attributes_hash, rest, last_line
end
```
[Haml parser.rb](https://github.com/haml/haml/blob/97a48651b8b8c2507096c1243d5f12abcb8e007b/lib/haml/parser.rb#L679-L705)

And here is `#balance_tokens`:

```ruby
def balance_tokens(buf, start, finish, count: 0)
  text = ''.dup
  Ripper.lex(buf).each do |_, token, str|
    text << str
    case token
    when start
      count += 1
    when finish
      count -= 1
    end

    if count == 0
      return text, buf.sub(text, '')
    end
  end
  raise SyntaxError.new(Error.message(:unbalanced_brackets))
end
```
[Haml parser.rb](https://github.com/haml/haml/blob/97a48651b8b8c2507096c1243d5f12abcb8e007b/lib/haml/parser.rb#L849-L865)

The algorithm works as follows:
1. Because the leading `{` was replaced with `a(`, there is no opening brace in the token stream. Haml initializes `count: 1`.
2. It iterates over the tokens returned by `Ripper.lex`.
3. When it encounters the closing token (`finish = :on_embexpr_end`), `count` decrements from `1` to `0`.
4. Once `count == 0`, it returns the slice of text up to that character. If the stream ends without `count` reaching `0`, it raises `SyntaxError: Unbalanced brackets`.


## The Divergence: Ripper vs. Prism

TruffleRuby does not use MRI's legacy C-based Ripper extension. Instead, to support tools built on Ripper, it uses `Prism::Translation::Ripper` - a compatibility layer provided by the new Prism parser that emulates Ripper's API and token stream.

So when Haml calls `Ripper.lex` on TruffleRuby, it is actually calling `Prism::Translation::Ripper.lex`.

Let's compare how CRuby's Ripper and Prism tokenize the same transformed attribute string `a(:selected => true}`:

**CRuby `Ripper.lex`:**
```ruby
require 'ripper'

Ripper.lex("a(:selected => true}")
# =>
[
  [[1, 0], :on_ident, "a", CMDARG],
  [[1, 1], :on_lparen, "(", BEG|LABEL],
  [[1, 2], :on_symbeg, ":", FNAME],
  [[1, 3], :on_ident, "selected", ENDFN],
  [[1, 11], :on_sp, " ", END],
  [[1, 12], :on_op, "=>", BEG],
  [[1, 14], :on_sp, " ", BEG],
  [[1, 15], :on_kw, "true", END],
  [[1, 19], :on_embexpr_end, "}", END]
]
```

**Prism `Prism::Translation::Ripper.lex`:**
```ruby
require 'prism'

Prism::Translation::Ripper.lex("a(:selected => true}")
# =>
[
  [[1, 0], :on_ident, "a", CMDARG],
  [[1, 1], :on_lparen, "(", BEG|LABEL],
  [[1, 2], :on_symbeg, ":", FNAME],
  [[1, 3], :on_ident, "selected", ENDFN],
  [[1, 11], :on_sp, " ", ENDFN],
  [[1, 12], :on_op, "=>", BEG],
  [[1, 14], :on_sp, " ", BEG],
  [[1, 15], :on_kw, "true", END],
  [[1, 19], :on_rbrace, "}", END]
]
```

Look closely at the final token:
- CRuby's Ripper returns `:on_embexpr_end` for the trailing `}`.
- Prism returns `:on_rbrace` for the trailing `}`.

Because Haml hardcoded `finish = :on_embexpr_end`, `count` was never decremented on Prism/TruffleRuby. The loop consumed the entire string without `count` ever reaching `0`, and Haml dutifully raised:

```text
Haml::SyntaxError: Unbalanced brackets.
```

The symptom was completely explained. But it opened a deeper question: why did CRuby emit `:on_embexpr_end` for a brace in the first place?


## Source Archaeology: Inside `parse.y`

Why did CRuby emit `:on_embexpr_end` instead of `:on_rbrace` when encountering an unmatched `}`?

In Ruby, braces are used in several distinct syntactic contexts:
- Hash literals (`{ a: 1 }`)
- Blocks (`items.each { |x| ... }`)
- Lambda literals (`-> {}`)
- String interpolation (`"Hello, #{name}"`)

Ripper produces distinct tokens for opening braces (`:on_lbrace`, `:on_tlambeg`, and `:on_embexpr_beg`), but reuses closing tokens: `:on_rbrace` (for hashes, blocks, and lambdas) and `:on_embexpr_end` (for string interpolation).

When parsing valid code, the parser knows whether a closing `}` corresponds to a hash, block, lambda, or string interpolation. But when parsing invalid code - like `a(:selected => true}` where a `}` appears without a matching `{` - the parser has to guess what the user intended.

Looking into CRuby's parser source (`parse.y`), we find the exact rule handling closing braces:

```c
case '}':
  /* tSTRING_DEND does COND_POP and CMDARG_POP in the yacc's rule */
  if (!p->lex.brace_nest--) return tSTRING_DEND;
  COND_POP();
  CMDARG_POP();
  SET_LEX_STATE(EXPR_END);
  p->lex.paren_nest--;
  return c;
```
[Ruby parse.y](https://github.com/ruby/ruby/blob/03b6d3f8898a28604fe6cb00eae3226b821168f4/parse.y#L11006-L11013)

The lexer tracks two separate nesting counters:
- `p->lex.paren_nest`: tracks total nesting depth (parentheses, brackets, braces).
- `p->lex.brace_nest`: tracks brace depth specifically.

When the lexer encounters `}` in `a(:selected => true}`, `brace_nest` is `0` because no corresponding opening `{` was ever seen. The condition `!p->lex.brace_nest--` evaluates to true, causing CRuby's lexer to return `tSTRING_DEND` (which maps to `:on_embexpr_end` in Ripper; see [`eventids2.c`](https://github.com/ruby/ruby/blob/03b6d3f8898a28604fe6cb00eae3226b821168f4/ext/ripper/eventids2.c#L265)).

It is worth noting that during standalone lexical analysis of invalid code, there is no single "correct" token. While a parser building an AST might understand higher-level grammatical structure, a lexer scanning a raw character stream cannot know what was intended when encountering an orphan `}`. Returning either `:on_rbrace` (closing a hash or block) or `:on_embexpr_end` (closing an embedded string expression) is a plausible heuristic. CRuby's lexer happened to default to string interpolation, whereas Prism's lexer chose a standard closing brace. The trouble only began when client libraries relied on CRuby's specific lexer heuristic as if it were a guaranteed language behavior.

### The Smoking Gun in MRI's Test Suite

Even more fascinating: this fallback was not accidental. While digging through CRuby's test suite, I found a test that explicitly references Haml:

```ruby
def test_trailing_on_embexpr_end
  # This is useful for scanning a template engine literal `{ foo, bar: baz }`
  # whose body inside brackes works like trailing method arguments, like Haml.
  token = Ripper.lex("a( foo, bar: baz }").last
  assert_equal [[1, 17], :on_embexpr_end, "}", state(:EXPR_ARG)], token
end
```

CRuby maintainers had deliberately codified this behavior into their test suite years ago to ensure template engines relying on the `a(` trick would continue to parse correctly!


## Fixing Prism's Ripper Emulation Layer

With the root cause identified, my first instinct was to patch `Prism::Translation::Ripper.lex` to mirror Ripper's behavior by returning `:on_embexpr_end` on unmatched braces ([ruby/prism#4164](https://github.com/ruby/prism/pull/4164)).

The fix was ready quickly, but the Prism maintainers preferred not to merge it.

While `Prism::Translation::Ripper` emulates the Ripper interface for backwards compatibility, faithfully replicating every obscure recovery quirk of CRuby's lexer on invalid syntax would add unnecessary complexity to the translation layer. From their perspective, that extra complexity was not justified - especially when the cleaner solution was for Haml to make its token-matching logic more robust.

They pointed out that an existing PR in Haml ([haml/haml#1210](https://github.com/haml/haml/pull/1210)) was already attempting to address TruffleRuby compatibility directly.


## Fixing Haml

A bit disappointed, I checked out the existing PR in Haml ([haml/haml#1210](https://github.com/haml/haml/pull/1210)). The situation didn't look promising: the PR had been waiting for review for over a month. When we finally pinged the Haml maintainer, he mentioned that while he was open to fixing TruffleRuby compatibility, he didn't like the approach taken in that PR and suggested redesigning it.

The initial fix counted `{` and `}` manually without using the `a(` substitution trick, assuming the attribute string was always a valid Ruby hash. But as we saw earlier, that breaks in cases like `%a{ user_attributes, foo: bar }`, where the attribute expression is not a valid hash literal.

"Great," I thought, "the PR author will update it soon, and the issue will be resolved." But the author didn't respond - not the next day, nor a week later. Seeing that the PR had stalled, I decided to pick it up and rework the fix myself in a new PR ([haml/haml#1212](https://github.com/haml/haml/pull/1212)).

The solution was straightforward:
1. Preserve the `a(` prefix trick so variable merging (`%a{ hash, key: val }`) continues to parse cleanly as method arguments.
2. Accept both token types: instead of expecting only `:on_embexpr_end`, match both `:on_embexpr_end` and `:on_rbrace` (along with all opening brace variants):

```diff
-        balanced, rest = balance_tokens(text.sub(?{, METHOD_CALL_PREFIX), :on_embexpr_beg, :on_embexpr_end, count: 1)
+        balanced, rest = balance_tokens(
+          text.sub(?{, METHOD_CALL_PREFIX),
+          [:on_lbrace, :on_tlambeg, :on_embexpr_beg],
+          [:on_rbrace, :on_embexpr_end],
+          count: 1
+        )
```

Now, regardless of whether `Ripper.lex` is backed by CRuby's native parser (emitting `:on_embexpr_end`) or Prism's translation layer (emitting `:on_rbrace`), `count` correctly decrements to `0` and extracts the balanced attribute slice.

The new PR was reviewed and merged quickly, bringing Haml back to a 100% test pass rate on TruffleRuby!


## Epilogue: Haml Migrates to Prism

Shortly after my fix, Haml migrated its parser from Ripper directly to Prism ([haml/haml#1214](https://github.com/haml/haml/pull/1214)).

Because Prism uses equivalent tokens for opening and closing brackets, the core attribute-parsing logic remained unchanged - the migration simply mapped the Ripper symbols to Prism's native constants:

```diff
         attributes_hash, rest = balance_tokens(
           text.sub(?{, METHOD_CALL_PREFIX),
-           [:on_lbrace, :on_tlambeg, :on_embexpr_beg],
-           [:on_rbrace, :on_embexpr_end],
+           [:BRACE_LEFT, :LAMBDA_BEGIN, :EMBEXPR_BEGIN],
+           [:BRACE_RIGHT, :EMBEXPR_END],
           count: 1)
```
